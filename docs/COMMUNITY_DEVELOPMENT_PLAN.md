# 成信友友：校园社区发展计划

版本：v0.2 · 3.1 首轮已本地实现，待发布验收

更新日期：2026-10-20

方向：校园社区为下一阶段重点，学习工具继续作为日常使用入口。

本文是产品与实施计划，不代表全部功能已经上线。3.1 首轮的本地实现、已验证范围与待发布事项见[实施记录](./COMMUNITY_MVP.md)；尚未推送或执行生产迁移。

## 1. 我们接下来要做成什么

成信友友不只帮同学“查信息”，也让同学能够围绕校园里的事物交流、互助，逐渐认识彼此。

下一阶段先跑通一个小而完整的闭环：

**统一公开身份 → 发布内容 → 收到回复 → 消息提醒 → 回来交流。**

课表、成绩、考试、图书馆等工具保留；社区沿用“校园”下的评分、二手、论坛三个入口，不再不断增加底部导航项。液态玻璃作为统一的界面材料与交互规范，不能影响点击、滚动、可读性和低性能设备体验。

优先级建议：先把身份和交流体验连起来，再扩展新的内容类型。用户已确认“校园社区”方向并要求实施 3.1，其余扩展仍属于建议方案。

## 2. 当前基础与缺口

以下是截至 2026-10-19 的代码与检查结果，不等同于所有客户端已经安装了相同版本。

| 领域 | 已有基础 | 下一阶段需要补齐 |
| --- | --- | --- |
| 学习工具 | 课表、成绩、考试、空教室、图书馆等已有实现 | 保持稳定，不让社区改造影响原有工具 |
| 评分 | 板块、对象、评分、评论与回复、举报等已有接口与客户端实现 | 统一作者资料；后续接入个人主页与互动消息 |
| 二手 | 出售、求购、详情、联系信息、状态管理已有基础 | 统一作者资料；暂不做订单、担保与支付 |
| 论坛 | 分类、帖子、回复、点赞、举报等已有基础 | 信息密度、统一身份、个人消息与收藏形成完整体验 |
| 用户身份 | 服务端已有 `rating_profiles`；社区内容关联该身份 | 昵称和头像可由用户维护，并与“我的”页面对齐 |
| 头像 | Flutter 已有账号隔离的本地头像和自定义图片能力 | 本地图片不等于公开头像，需要经用户确认同步到服务端 |
| 公告 | 已有平台公告、后台管理与应用内展示 | 公告不是个人消息，也不是系统级推送 |
| 客户端 | Vue Web/PWA 与 Flutter Android/iOS 并存 | 统一接口兼容策略、版本对应关系与真实设备验收 |
| 发布 | 已有官网、安卓下载入口和 iOS TestFlight 入口 | 核对实际安装包、基础包、热更新补丁与源码版本的对应关系 |

当日检查中 Flutter 330 项测试、静态分析，以及 Web 408 项测试、lint、类型检查和构建通过。这是当时工作区的基线，不代表后续改动自动通过，也不能代替设备验证。

部分图片加载、原生热更新等工作仍存在本地未提交或未发布改动。不能以“本地可用”推断“线上已可用”；上线前必须重新核实。

## 3. 第一轮做什么、不做什么

### 3.1 第一轮推荐范围

1. **公开资料统一**：公开昵称、头像、简单个人主页；评分、二手、论坛显示同一份资料。
2. **互动消息**：首版只做论坛帖子收到回复、回复收到回复，以及未读管理。
3. **我的收藏**：首版只收藏论坛帖子，提供收藏列表和取消收藏。
4. **基础治理与稳定性**：举报、内容可见性、写入限流、账号隔离、版本兼容和发布检查。

昵称头像统一覆盖已有社区模块；消息、收藏先限定论坛，避免一次改动所有互动链路。评分回复提醒、二手收藏等可在首轮验证后追加。

### 3.2 暂不进入首轮

- 实时私聊、群聊、关注关系和算法推荐流。
- 订单、收款、担保交易、平台代管资金。
- APNs/FCM 等系统级推送，以及后台必达承诺。
- 广泛的校园 AI 助手、课程资料大规模共享。
- 自动公开学号、真实姓名、成绩、课表或联系方式。
- 为社区再建一套账号、密码和登录流程。

点赞提醒、`@` 提及、个人简介也先不作为首轮必需项，减少通知噪声、骚扰和内容审核成本。

## 4. 分阶段实施

阶段以验收结果推进，不预设固定日期。开发排期应在发布基线整理和接口确认后，根据实际可投入时间确定。

### M0：先建立可追溯的发布基线

目标：知道用户正在用什么版本，问题出现时能复现、回退。

- 整理现有未提交改动，按各自任务分别验收，不将无关工作混入社区改造。
- 核实图片缩略图接口与客户端加载改动的状态，按兼容顺序发布。
- 建立版本记录：源码提交、服务端提交、客户端基础包、补丁版本、下载地址、安装包摘要、发布日期。
- 核对官网 APK 与原生基础包的版本、签名和摘要；不能仅根据文件名判断实际内容。
- 核对 TestFlight 实际可安装版本及其更新机制，不把本地开发签名验证等同于 TestFlight 验证。
- 补充 Flutter 的分析、测试和构建检查；现有 Web/旧封装工作流不能替代 Flutter 检查。
- 使用独立测试账号、测试安装和测试数据；涉及真实用户数据前先备份并验证恢复路径。

验收：任一线上问题能够对应到具体源码和安装包；至少完成 Android、iOS 的安装、冷启动、重新登录、账号切换、弱网和导航点击验证；阻断发布的问题有明确结论。

### M1：统一公开昵称、头像与个人主页

目标：大家能认出同一个人，不再出现“我的页面一个头像，帖子里另一个头像”。

- 扩展现有 `rating_profiles`，不另建重复用户表；继续使用现有社区认证与稳定的公开身份 ID。
- 允许修改公开昵称、选择预设头像或上传自定义头像。
- “我的”页面主要展示区使用公开昵称与头像；学籍卡片保留学校姓名等私有信息，避免混淆。
- 第一次同步本地头像时展示公开范围说明，由用户确认后上传；取消后不上传。
- 评分、二手、论坛作者统一读取公开资料，修改后历史内容也能显示新资料。
- 增加只对已登录社区用户可见的个人主页。首版展示公开资料与其公开、正常展示的论坛帖子；评分和二手内容聚合留到后续。
- 无自定义头像时使用预设头像；不将学号、学校照片、学籍姓名自动填入公开资料。

技术要点：

- 兼容现有 `display_name`、`avatar_preset`，新增头像资源标识及资料版本字段；旧客户端继续可用。
- 昵称在服务端校验长度、空白、控制字符等；按普通文本渲染，不作为 HTML。
- 修改采用版本校验，避免两台设备相互覆盖；失败时保留原资料并允许重试。
- 头像资源校验归属、用途、文件实际类型与大小；明确公开头像和普通附件的访问规则。
- 将头像引用纳入资源引用/清理机制，替换头像后不能误删仍被使用的资源。
- 根据资料版本刷新作者缓存，避免每条帖子保存一份长期过时的昵称、头像快照。
- 历史默认昵称保留兼容；是否批量调整需另行确认，不擅自替用户改名。

验收：用户修改后，“我的”、三类社区内容作者与个人主页一致；旧客户端不报错；第二个账号看不到第一个账号的私有资料和缓存；未确认前没有本地图片上传。

### M2：论坛互动消息

目标：有人回复后，用户能知道并顺利回到讨论现场。

首版事件：

- 有人回复我的帖子，通知帖子作者。
- 有人回复我的回复，通知被回复者；若同时符合两条规则，同一次操作对同一个接收者只生成一条消息。
- 自己回复自己不通知；点赞、浏览、获取二手联系信息不产生消息。

交互：

- “校园”顶部提供克制的消息入口；有未读时显示小红点或统一规格的计数。
- 消息列表包含操作者公开资料、动作、内容简短摘要、时间和已读状态。
- 点击跳转到帖子及对应回复；目标删除、隐藏或权限变化时显示“内容暂不可见”，不显示过期摘要泄露内容。
- 支持单条已读、全部已读；全部已读只覆盖请求开始时确定的消息范围，期间新到的消息仍未读。
- 首版仅在进入页面、回到前台和用户手动刷新时拉取，合并并节流请求；不使用常驻轮询或承诺后台必达。

可靠性与安全：

- 消息生成与成功的业务写入保持一致；采用同一数据库事务，或确有异步需求时采用持久事件表。不能业务失败却发出消息。
- 使用事件与接收者去重标识，重试、并发提交不会重复通知。
- 消息查询、未读计数和已读操作均按当前认证身份授权，不能只凭消息 ID 操作。
- 过滤不可见内容；用户被限制、内容被下架后，旧消息不能成为绕过权限的入口。
- 切换账号、退出登录和切换服务地址时清空个人消息缓存并取消旧请求，迟到响应不能写回新账号。
- 消息与平台公告分开存储和管理，不继承公告“最多自动提醒两次”“退出后保留匿名缓存”等规则。

验收：两个测试账号完成发帖、回复、查看、跳转、已读全流程；重复请求不重复通知；全部已读与新消息并发时不误清；删除内容后不泄露正文；无自我通知、跨账号访问或缓存串号。

### M3：我的收藏

目标：有用的帖子不再只能靠搜索找回来。

- 帖子详情提供收藏/取消收藏；“我的”提供收藏列表。
- 首版仅支持论坛帖子；数据结构保留目标类型，之后可以扩展评分板块和二手商品。
- 同一用户对同一目标只能有一条收藏；添加与取消均可安全重试。
- 收藏默认私密，不显示“谁收藏了我”，不向作者发送提醒。
- 收藏目标被删除、隐藏或失去访问权限后，只显示不可用提示或移除入口，不保留可泄露原文的预览。
- 网络失败应回滚错误的选中状态；列表与详情状态一致。

验收：重复点击、弱网重试、退出后重新进入、多设备操作结果一致；只能访问自己的收藏；无法收藏不存在或不允许访问的内容。

### M4：小范围验证后扩展失物招领

这是推荐的下一项新增能力，是否启动根据首轮体验和反馈决定。

优先在论坛里增加结构化帖子类型，不新增一个独立 App 模块：

- 类型：寻物、招领。
- 字段：物品类别、校区、时间、模糊地点、图片、可选联系方法。
- 状态：寻找中、已找回/已认领、已关闭，由发布者维护。
- 列表可按校区、类型和状态筛选；普通讨论帖仍可正常使用。
- 提醒用户遮挡证件号、二维码、银行卡和联系方式；认领核验细节不在公开帖中完整披露。
- 不自动转换旧帖子，不替用户公开原本未公开的联系方式。

验收：发布、筛选、更新状态、举报、关闭完整可用；没有敏感字段被自动公开；闭环完成后不会长期以“寻找中”误导其他用户。

## 5. 页面与组件安排

| 位置 | 建议变化 | 保持不变 |
| --- | --- | --- |
| 底部导航 | 不增加入口 | 课表、工具、校园、我的 |
| 校园顶部 | 保留低存在感分段切换，加入小型消息入口 | 评分、二手、论坛三个内容区 |
| 论坛列表 | 紧凑标题、摘要、作者、时间、回复和点赞信息 | 优先显示内容，不把装饰标题放大 |
| 帖子详情 | 可点击作者、收藏、回复定位 | 举报、删除等原有权限 |
| 我的 | 公开资料编辑、我的消息、我的收藏 | 学籍信息继续作为本人私有信息展示 |
| 个人主页 | 公开资料与可见论坛帖子 | 不展示对方学号、成绩、课表或私有收藏 |

延续通用液态玻璃组件，统一导航、分段选择和浮层；内容阅读区域保持清楚的对比度。消息、收藏不各自再写一套玻璃效果。触控热区至少 44 逻辑像素，兼容大字体、减少动态效果和深色模式。

## 6. 服务端与数据设计建议

以下是设计草案，表名和接口路径在实施前最终确认，不是已经可调用的接口。

### 6.1 数据结构

| 对象 | 处理方式 | 关键约束 |
| --- | --- | --- |
| 公开资料 | 扩展现有 `rating_profiles` | 稳定公开 ID；昵称、头像资源、资料版本、更新时间；不复制学籍信息 |
| 头像资源 | 复用现有附件能力并补充用途和引用管理 | 校验归属；限制格式与大小；引用存在时不可误清理 |
| 个人消息 | 新增个人消息表 | 接收者、操作者、事件、目标、去重键、创建序号、已读状态；按接收者查询 |
| 收藏 | 新增私有收藏关系表 | 用户 + 目标类型 + 目标 ID 唯一；服务端复核可见性 |
| 屏蔽关系 | 在扩大开放前补齐 | 作用范围、取消屏蔽和直接访问规则明确，不影响举报受理 |

继续使用现有社区认证身份，不把学号或认证 subject 作为对外个人主页地址。公开资料接口只返回允许公开的字段，不能直接序列化整个数据库记录。

### 6.2 接口职责

可考虑独立 `/api/v1/community` 模块，承担以下职责：

- 查询、修改本人公开资料；查询指定公开 ID 的公开资料与可见帖子。
- 查询本人消息、未读计数；单条已读；按服务端确认的消息序号水位批量已读。
- 查询本人收藏；幂等添加和取消收藏。

沿用已有认证与错误返回规范；分页、限流、版本冲突、资源不可见均有稳定错误码。本人接口明确禁止共享缓存。

若新增此前不存在的接口前缀，需要同时更新代理、网关、跨域与部署检查，不能只写控制器。客户端不能仅凭返回状态码成功就假设响应格式正确。

### 6.3 迁移与兼容

- 优先使用新增字段/表，保留旧字段和预设头像回退，不在首轮移除旧客户端依赖。
- 按实施时的最新迁移序号新增脚本，同时更新显式迁移执行清单、部署包和测试。
- 上线前备份，先在测试环境跑迁移并检查耗时、索引、默认值与历史数据。
- 先部署兼容服务端，再发布依赖新接口的客户端；通过开关分阶段开放新入口。
- 回退优先关闭新功能、回退应用版本；不要通过删除新表/字段丢弃已产生的用户数据。

## 7. 多端顺序

1. 服务端先提供向后兼容的接口与权限检查。
2. Flutter Android/iOS 先在测试版本完成完整流程，真实设备验证后再逐步开放。
3. Vue Web/PWA 同步兼容公开作者资料；个人消息和收藏入口按能力开放。未支持的页面提供明确提示，不跳到不存在的路由。
4. 官网描述只更新已发布、已验收的能力，不提前宣传讨论稿功能。
5. Harmony 继续按独立适配计划推进，不将现有工程骨架当作已经验证的安装包；Flutter Web 也不默认视为已验收客户端。

各端不能重新生成彼此独立的社区身份。版本落后时允许基础阅读和旧头像回退，不能因为一个可选资料字段缺失而导致整个社区无法打开。

## 8. 内容安全与运营边界

- 复用已有举报、管理隐藏/删除能力，并检查论坛、个人主页、消息、收藏四个入口都遵守同一可见性规则。
- 给发帖、回复、改昵称、上传、消息生成设置合理限流；只做客户端限制不算完成。
- 首轮使用邀请体验；扩大开放前补齐可理解的屏蔽/拉黑能力、处理入口与简单社区规则。
- 删帖、封禁和个人资料修改需要可追踪，但日志不记录密码、完整令牌或不必要的学籍数据。
- 明确账号退出与社区内容删除不是一回事；提供删除本人内容及申请处理账号数据的路径，说明必要留存的范围。
- 不制造虚假帖子、虚假评分和假活跃；示例数据仅在隔离测试环境使用。
- 二手仍是信息发布与联系平台，不因为增加公开身份就宣称已完成实名担保。

## 9. 验收与上线门槛

| 方向 | 必测场景 |
| --- | --- |
| 身份与隐私 | 公开与学籍信息分离；未确认不上传头像；不同账号、不同服务地址不串缓存 |
| 授权 | 猜测他人资料管理、消息、已读、收藏 ID 均不能越权；公开接口只返回公开字段 |
| 互动可靠性 | 自我回复、嵌套回复、重复提交、事务失败、删除目标、并发全部已读 |
| 数据一致性 | 修改头像昵称后历史作者更新；收藏详情/列表一致；旧客户端可回退 |
| 网络 | 首次加载、离线、慢网、超时、接口返回非预期内容、重试和账号切换中的迟到响应 |
| 界面 | 深浅色、顶部安全区、冷启动、导航连续点击、胶囊拖动后点击、大字体、键盘与返回 |
| 附件 | 错误格式、超大文件、无权限资源、替换头像、清理任务、图片加载失败 |
| 发布 | CI、迁移演练、Android/iOS 实机、旧版本兼容、功能关闭和回退演练 |

已知越权、串号、敏感信息泄露、数据丢失问题必须归零后发布；登录失败、核心导航失效等阻断问题不得带入公开发布。其他遗留问题记录影响、临时方案和负责人。

建议发布链路：测试环境 → 内部双账号验收 → 服务端兼容发布 → 原生测试版本 → 小范围体验 → 分批开放。每一步保留版本记录；服务端健康检查使用 `/api/v1/ratings/health`，不以其他服务的健康响应代替。

## 10. 如何判断方向有没有价值

先看交流有没有真正发生，不先追求功能数量和表面日活。小范围体验建议观察：

- 有多少真实用户愿意设置公开昵称、头像并发布有效内容。
- 已发布满 24 小时的有效帖子中，有多少获得了其他用户的有效回复。
- 用户看到互动消息后，是否回到原帖继续交流。
- 收藏后是否会回来阅读，找不到旧内容的反馈是否减少。
- 举报、骚扰、误通知、加载失败和崩溃是否增加。

排除管理员、测试账号和演示数据；只收集必要的事件计数，不将学号、成绩、课程和正文作为分析字段。新增分析采集、保存期限与隐私说明应单独确认，不因写入计划就自动启用。

## 11. 后续功能候选池

| 功能 | 价值 | 启动条件 |
| --- | --- | --- |
| 失物招领 | 需求具体、容易形成互助闭环 | 首轮交流体验稳定，有人维护状态和举报 |
| 评分回复提醒、二手收藏 | 串联现有模块，复用消息和收藏基础 | 论坛消息准确、可见性与目标类型扩展测试完成 |
| 校园活动/搭子 | 帮助同学找到同行者 | 有真实需求；先定义报名、退出、联系方式和骚扰处理 |
| 官方通知订阅 | 减少信息分散 | 来源、授权、更新时间和失效提示能够保证，不冒充官方 |
| 自愿空闲时间匹配 | 工具与社区联动 | 必须由用户主动选择分享，先定义最小披露范围 |

私聊不是永远不做，但应在出现稳定交流需求、具备反骚扰与运营资源后重新评估。不要为了留住用户强迫公开真实身份或私有学业信息。
